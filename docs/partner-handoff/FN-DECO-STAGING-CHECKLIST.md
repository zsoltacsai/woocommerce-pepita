# FN-DECO Staging Verification Checklist & Protocol

**Environment:** FN-DECO WooCommerce **staging** only. Production is out of scope (NO-GO).
**Plugin artifact:** `dist/wp-pepita-sync.zip` built from the **exact release commit**.
**SHA-256 of the ZIP:** *not recorded in this document.* Take the digest from `dist/wp-pepita-sync.zip.sha256` produced for that exact release commit (`bin/build.sh`; reproducibility: `bin/verify-reproducible.sh`) and compare it with the file you upload. Never copy a hash from an older document or a different build.
**Catalog target:** the real product counts (total / exportable / excluded) are **to be established by this staging run and recorded in the evidence section below.** Earlier drafts quoted "269 → 241 (28 excluded)"; those figures came from a synthetic fixture and are **not** verified FN-DECO staging results (see `docs/autonomous-development/PEPITA-HANDOFF.md`).

> Read [INTEGRATION-GUIDE.md §6 "Documented limits"](INTEGRATION-GUIDE.md#6-documented-limits) first. UI labels below follow the current admin screens (Hungarian); if a label differs, use the screen with the same slug.

### Documented limits (summary — full text in the Integration Guide)

- **Order API: not approved for live traffic.** It must stay disabled for production. The code default is *enabled* with an auto-generated key, so it has to be switched off explicitly (or feed-only beta mode used) everywhere except the sandbox test in Phase 6.
- **Test orders only on staging/sandbox with synthetic data** (e.g. `*@example.test`, synthetic SKUs, throw-away key). No real customers, no live Pepita dispatcher.
- **Feed:** staging feeds contain staging URLs. Before a Pepita import, validate a feed built with the **real, non-staging product and image URLs** (publicly reachable images, JPEG/PNG ≥ 1200×630). Passing plugin validation is not proof that Pepita accepts the feed (**verify with Pepita**).
- **GTIN:** never generated by the plugin; digits must be 8/12/13/14 (length check only). Category GTIN requirements and category mapping must be confirmed with Pepita.
- **Reconciliation:** Pepita import errors are reconciled manually against *Hibás termékek* / *Feed ellenőrzés* (Integration Guide §6.4).
- **Full/stock consistency:** the stock feed is withheld if it does not match the last full feed; import the full feed first.
- **Operational exports are not "PII-free"**: no raw free-text errors and hashed untrusted identifiers, but they still hold order IDs/timestamps/statuses.

## Phase 0: Gate — order intake closed

- [ ] Staging store: confirm no real Pepita dispatcher is configured to call this host.
- [ ] *Pepita → Beállítások → Rendelés API*: confirm the intake checkbox is **off** (or feed-only beta mode is on) **before** anything else. Expected: any POST to the order route returns `503`.
- [ ] Record who set it and when. It is switched on only temporarily in Phase 6 and switched off again at the end of Phase 6.

---

## Phase 1: Pre-deployment server verification

- [ ] **PHP:** 8.1 or newer (plugin header `Requires PHP: 8.1`). Extensions/libraries needed for image handling: GD or Imagick (see `INSTALLATION.md`; verify any further extension requirement there rather than from older drafts).
- [ ] **WordPress ≥ 6.4**, **WooCommerce ≥ 8.2** (plugin header). HPOS enabled **or** legacy storage — record which one was tested.
- [ ] **Memory limit:** record the configured `memory_limit` and whether the full feed generation completes (no number is guaranteed by the code).
- [ ] **Database/storage permissions:** `wp-content/uploads/` writable; DB user can `CREATE TABLE`/`ALTER`/`INSERT`/`UPDATE`/`DELETE`.

---

## Phase 2: Plugin installation & activation

- [ ] Upload `dist/wp-pepita-sync.zip` via *Plugins → Add New → Upload Plugin*.
- [ ] Compute the SHA-256 of the uploaded ZIP and compare it with `dist/wp-pepita-sync.zip.sha256` **of the exact release commit**. Record both values and the commit SHA in the evidence section.
- [ ] Activate the plugin.
- [ ] Verify DB initialization: table `{$wpdb->prefix}wps_pepita_orders` exists with a **unique key on `external_id`** and keys on `status`, `wc_order_id`, `created_at` (`includes/class-installer.php:99-117`).
- [ ] Verify the private storage directory `wp-content/uploads/wps-pepita-<storage key>/` was created (feeds, pointer, `labels/`), and that `wp-content/uploads/wps-derivatives/` appears once WebP derivatives are generated. Verify directory-listing/script guards (`.htaccess` / `index.php`) are present.
- [ ] Confirm the plugin generated an Order API key (do **not** write the key into tickets/chat/docs).

---

## Phase 3: Merchant profile configuration

- [ ] *Pepita → Eszközök és riportok*, card **Konfigurációs profil importálása**: choose `fn-deco-staging-profile.json` and press **Profil feltöltése és előnézet**.
- [ ] Verify the preview (`?page=wps-pepita-tools&wps_preview=1`): checksum status "Sértetlen"; settings and category-rule diffs shown; **store settings unchanged** at this point.
- [ ] Confirm the profile did **not** change the Order API state (it is not a portable setting) and contains no secrets.
- [ ] Press **Módosítások jóváhagyása és alkalmazása**; verify the settings were applied and the staging transient was removed.

---

## Phase 4: Full feed generation & exclusion verification

- [ ] *Pepita → Feedek*: press **Teljes feed generálása**.
- [ ] Record: total products scanned, exported, excluded (**actual values**; compare with the merchant's expectation, do not assume 269/241/28).
- [ ] *Pepita → Hibás termékek*: reconcile every excluded product with a reason code (see [ERROR-CODES.md §2](ERROR-CODES.md#2-feed-validation-per-product)): e.g. `missing_image`, `invalid_gtin`, `gtin_required`, `missing_category`, `invalid_price`. Image-size findings (`insufficient_image_dimensions`) are warnings, not exclusions.
- [ ] *Pepita → Feed ellenőrzés*: review KPIs and download the CSV for the evidence file.
- [ ] Download the full feed through the tokenised URL (`/?wps_feed=full&token=…`) and inspect structure against Pepita's XML specification (`docs/m9d/pepita-official-spec.html`, `docs/m9d/PEPITA-XML-CONTRACT-MATRIX.md`).
- [ ] Verify WebP derivatives exist under `wp-content/uploads/wps-derivatives/`.
- [ ] **Real-URL validation (mandatory before any Pepita import):** the staging feed contains staging URLs. Generate/inspect a feed with the **real, non-staging product and image URLs** and check that every image URL is publicly reachable (HTTP 200, JPEG/PNG, ≥ 1200×630). Do not hand a staging-URL feed to Pepita.
- [ ] GTIN: for every category Pepita requires GTINs for (**verify with Pepita**), confirm products carry real GTINs and the category is flagged "GTIN required" in the plugin. No GTIN may be invented.
- [ ] Category mapping: confirm with Pepita that each exported category hierarchy is accepted.

---

## Phase 5: Stock feed verification

- [ ] *Pepita → Feedek*: press **Készletfeed generálása** (after a successful full feed).
- [ ] Verify the stock feed publishes (it is withheld with an explanatory message if the catalog signature differs from the last full feed — then regenerate the full feed first).
- [ ] Confirm product IDs, prices and quantities in the stock feed match the same products in the full feed generation just produced. Record generation timestamps.
- [ ] Record the generation time (no fixed time budget is guaranteed by the code).

---

## Phase 6: Order API sandbox test (staging only, synthetic data only)

Prerequisites: Phase 0 recorded; the staging store has a **synthetic published simple product** with a known SKU (e.g. `SKU-1`); the test uses a throw-away key; **no real customer data**; no live Pepita dispatcher involved. Request and response formats: [API-CONTRACT.md](API-CONTRACT.md) (code-verified, not executed).

- [ ] Temporarily enable the intake (and leave `order_api_require_https` **on**). Use the staging key from *Pepita → Rendelés API*.
- [ ] Prepare `synthetic-order.json` from the example in API-CONTRACT.md §3.4 (adapt `sku`, product `id`, VAT to the staging tax setup; e-mail on `example.test`).
- [ ] Send it:
  ```bash
  curl -sS -i -X POST 'https://<STAGING-HOST>/wp-json/wps/v1/pepita/order' \
    -H 'Content-Type: application/json' \
    -H 'X-WPS-Api-Key: <STAGING_ORDER_API_KEY>' \
    --data @synthetic-order.json
  ```
- [ ] **Created:** HTTP `200`, body `{"isError":false,"responseCode":200,"message":"A rendelés sikeresen fogadva.","orderId":<n>}`.
- [ ] In WooCommerce verify: one new order, status `processing` (paid) or `on-hold` (unpaid) unless the status settings differ; line items, quantities, gross prices/taxes, shipping and voucher match the payload; billing/shipping data are the synthetic values; no customer e-mail was sent.
- [ ] **Identical replay:** send the same file again → HTTP `200`, same `orderId`, message says the order was already imported; **no second order**.
- [ ] **Conflicting replay:** change one value (e.g. quantity) but keep the `id` → HTTP `409`, message "…az új értesítés tartalma eltér…"; the existing order is unchanged and carries an operator note; `order_duplicate` warning in *Napló*.
- [ ] **Negative tests** (expect, per contract): wrong key → `401`; no/unknown SKU → `422` and no order; invalid JSON → `400`; HTTP instead of HTTPS → `403`; repeated wrong keys (> 30/min) → `429`; switch intake off → `503`.
- [ ] Optional: send a tiny valid base64 PDF as `package_label` and confirm it is stored under the private `labels/` directory and downloadable only for `manage_woocommerce` users; an invalid label must **not** fail the order.
- [ ] **Switch the intake off again** and delete the synthetic orders/key as appropriate. Record the final state.
- [ ] Record Pepita-side behavior that cannot be tested here as **open — verify with Pepita**: dispatcher retry policy on `409`/`5xx`, amendment/cancellation flow, header vs. query-parameter key delivery.

---

## Phase 7: Operational reports & cleanup

- [ ] *Pepita → Eszközök és riportok*: verify the operational summary (orders, successes, failures, orphans, GMV).
- [ ] Press **Operációs riport letöltése (.csv, nyers hibaszövegek nélkül)**. The CSV has the columns: Pepita ID, WC Order ID, Origin, Status, Attempts, Created At (UTC), Updated At (UTC), Error Code, Error Explanation (`Operational_Reports::export_report_csv()`; re-check against the build under test).
- [ ] Verify in the CSV: **no raw free-text error messages** (only fixed codes such as `replay_conflict`, `sku_not_found`, `validation_error`, `unclassified_error`); Pepita IDs not matching `^[A-Za-z0-9_-]{1,64}$` appear as `hash:…`; unusual origins appear as `other`; cells starting with `=`, `+`, `-`, `@` are neutralised with a leading `'`.
- [ ] Do **not** describe the export as "PII-free": it still contains order identifiers, WC order IDs, timestamps and statuses; restrict it to authorised staff.
